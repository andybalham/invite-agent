# E2E suite tiers, coverage boundaries, and runtime budgets

## Scope and delivery status

T-130 / S-050 / E-014 specifies the browser suite selections and performance expectations. The [T-128 isolation boundary](e2e-isolation-contract.md) and [T-129 resource lifecycle](e2e-run-lifecycle-contract.md) apply to every tier, worker, attempt, direct invocation, and foundation/discovery browser stage. A smaller selection, fresh organiser identity, or read-only test does not authorize shared-table writes. Every managed invocation must validate its owned targets, preserve evidence, and confirm cleanup; a fast passing browser result with failed cleanup is a failed run.

T-134 implements efficient seeds; T-135 separates targeted invariants from complete integrity comparisons; T-136 splits discovery cases and repeated viewport setup; T-137 benchmarks concurrency and implements budget enforcement; T-138 wires suite commands/selections; T-139 migrates CI/documentation; T-140 verifies acceptance, repeatability, and no leftovers. The current commands and CI behavior are documented in [isolated E2E CI and operations](e2e-ci-and-operations.md); this contract remains the coverage and runtime reference.

## Tier selection contract

The four selections below describe coverage, not new CLI spellings. T-138 must expose explicit selections and make the ordinary E2E default fast. Stable case metadata/projects or equivalent selection must separate cases inside a mixed spec; selecting all of `my-polls-search.spec.ts` cannot implement the fast/discovery boundary. Listing each implemented selection must make included cases reviewable.

| Tier | Intended use and required coverage | Coverage boundary |
| --- | --- | --- |
| Fast default regression | Routine local change and PR browser gate. All focused poll workflow specs, bounded dashboard search/navigation/lifecycle checks on desktop and mobile, and basic dense Load more behavior. | Excludes the full T-119 cross-product, 201-candidate sparse setup, repeated complete comparisons over large datasets, smoke, and the deliberate diagnostics probe. It remains a real API/DynamoDB regression suite. |
| Smoke journey | Explicit full application journey, onboarding/release sanity and isolated-run repeatability. Only SM-01 through SM-11 in `smoke.spec.ts`, in order on a fresh UI-created poll with an owner and two independent public contexts. | One representative lifecycle, not all acceptance examples. No large fixture seed, discovery matrix, mobile matrix, load benchmark, or production assurance. |
| Discovery | Explicit focused My polls verification across pure rules, frontend components, real API/repository, and bounded browser journeys. Includes the dashboard subset of fast regression and representative dense pagination. | Does not implicitly select smoke, unrelated poll specs, the full browser matrix, sparse 201-candidate fixture, or large complete-storage comparisons. Exhaustive rule/API permutations may remain at lower layers when cheap; expensive pagination/integrity cases require explicit exhaustive selection. |
| Exhaustive pagination/integrity | Explicit comprehensive discovery acceptance, storage/index/audit changes, pre-release evidence and periodic CI verification. Full T-119 browser matrix, real sparse continuations, complete accumulated pages and dedicated complete storage/history comparisons. | This is additional coverage, not a replacement for fast, smoke, or lower-layer checks. Selecting exhaustive must not silently rerun every fast test or the smoke journey. |

The focused discovery browser subset intentionally overlaps fast regression so dashboard work can be verified independently. A future aggregate run may deduplicate identical cases, but must report which tier obligations they satisfy. An aggregate acceptance result requires all four tiers plus applicable foundation/component/integration gates; no single tier's success establishes the whole release contract.

### Smoke boundaries

The [local smoke contract](local-smoke-test-contract.md#checkpoints-and-acceptance-traceability) remains authoritative for SM-01 through SM-11, fixed inputs, per-write revisions, read-only/cancel/rejection snapshots and diagnostics. Retain My polls entry/title/return and refreshed singleton summaries; UI draft/date creation, preview, publication/copy; two public views collaborating; duplicate rejection; safe location; history/undo; owner access denial; close/freeze/reopen/reclose; and revoked-link rejection. All eleven checkpoints must complete to pass. Do not replace UI writes under test with fast seeds or trim its complete history checks to meet a budget.

One poll cannot prove multi-poll ordering, foreign-owner list exclusion or pagination. Smoke does not replace detailed date/name/location/ranking/undo/auth matrices. SM-11 uses the documented local repository revocation hook; it does not prove organiser token regeneration. Structured history value cells still have the documented rendering limitation. No tier establishes native browser-cache acceptance, Cognito sign-in, deployed AWS routing/IAM, all browser engines/devices, or production load behavior; those retain the [T-127 delivery limits](t127-verification.md#production-readiness-limits).

### Exhaustive cases and integrity guarantees

Retain these as explicit cases with separately reported durations, so optimizing the default cannot hide a coverage loss:

1. **T-119 full matrix:** preserve 4 filters x 15 modes from [independent discovery expectations](../test/support/my-polls-discovery-cases.mjs), exact ordered IDs across every continuation, no duplicate/omitted IDs, page exhaustion, private/no-store summaries, bodyless GETs and owner headers. Retain missing/capability-only identity denial, foreign-owner cursor rejection, foreign owner's valid first-page results and unauthenticated UI behavior. Keep complete live API/browser agreement; pure rules alone are insufficient. Both desktop and mobile retain the existing matrix assertions. Equivalent read-only viewports may reuse one deterministic owned dataset serially with independent browser/query state instead of reseeding it twice.
2. **Sparse candidate budget:** retain 201 newer nonmatches ahead of 26 older Open matches, the Closed match and foreign-owner sentinel. A real database query must return an empty page with a continuation before matching pages of 25 and 1, for Active and Open; Closed membership and clearing must also follow continuation. Verify ordered accumulated IDs, no loops/duplicates/omissions, More polls may match versus exhausted no-match, query/page reset, and page-two title return retaining filter/search but refetching page one. Preserve both viewport assertions while avoiding duplicate large seeds where safe. Mocked empty pages do not replace this case.
3. **Complete read-only integrity:** around representative list/filter/search/navigation/auth-denial sequences, compare consistently read, fully paginated app/audit partitions for selected owned and foreign sentinel polls, including metadata/version, immutable `createdAt`/creation keys, participant/name records and every prior event. Cover the full large discovery dataset at a dedicated before/after boundary rather than resnapshotting it after every query. Where capability records live outside `POLL#` partitions, include explicit capability-key checks or the existing dedicated publication tests; a partition comparison alone proves nothing about those keys.
4. **Mutation and immutable-history integrity:** an older poll's intentional edit advances only its expected version/revision while preserving original creation keys and all prior events; unrelated peers stay unchanged. Retain lifecycle create/save/publish/participant/close/reopen event identities, contiguous revisions, expected actor/action and exact append-only history. Read every history continuation and ensure no omissions, duplicated revisions or rewritten events. [Audit-history](../test/integration/audit-history.test.mjs), [undo](../test/integration/undo.test.mjs) and [My polls lifecycle integration](../test/integration/my-polls-lifecycle.test.mjs) provide existing dedicated lower-layer coverage; small browser history remains in fast and complete smoke history remains in smoke.

Detailed cursor tampering/expiry/query-owner binding, equal-creation-instant ID tie-breaks, stale index metadata rechecks, corruption rejection, eventual consistency and transaction contention retain foundation/API/repository coverage. Stale browser replies, identity changes, pending/loading, first/later-page failure and same-cursor retry retain [search](../test/component/my-polls-search.test.mjs) and [loading](../test/component/my-polls-loading.test.mjs) component coverage. A bounded live dense/sparse journey supplies the real stack boundary; artificially repeating every fault on both live viewports is not required.

## Fixture, invariant, worker, and retry expectations

Fast and focused discovery use the smallest dataset proving the behavior: normally a handful of polls/participants, at most the 26 matches needed for a dense two-page boundary plus explicit sentinels. Hundreds of distractors belong only to sparse/exhaustive coverage. T-134 may seed fixtures through deterministic repository/SDK helpers when HTTP creation/publication/closing is incidental; those helpers must produce valid normal schemas, indexes, counts, versions and audit data in the validated owned pair. Focused creation/publication/lifecycle tests and smoke retain their UI/HTTP transitions under test. Seeding must not use a production setup endpoint or mutate the dataset during read-only viewport comparisons.

T-135 must keep targeted read-only evidence in fast/discovery: observed GET-only requests, unchanged authoritative versions/audit totals, immutable creation metadata/index keys, expected owner-scoped IDs/order/counts, and unchanged foreign sentinels. Network observation alone cannot detect writes caused by a GET. Check accepted writes' expected version/event increments and rejected/cancelled writes' unchanged state. Complete large app/audit comparisons move to dedicated integrity coverage; this is not permission to remove immutable-history assertions. Whole-table teardown under T-129 needs ownership/absence evidence, not snapshots of every poll.

All tiers initially use Chromium, **one explicitly selected Playwright worker and zero retries locally and in CI**. Serial execution is the reproducible baseline given the README's known collaborative-availability contention. Multiple public contexts inside a case are behavior under test, not additional workers. Discovery/exhaustive real-DynamoDB Node stages initially use test concurrency 1; this does not prescribe concurrency for pure foundation tests.

T-137 must benchmark 1 and 2 workers (4 only if 2 is stable), retaining all cases, seeds, waits and retry settings, before selecting higher concurrency. Do not inherit CPU-based worker defaults. Evaluate wall time, slow cases, DynamoDB/transaction contention, failures and cleanup across successive runs. Each test/worker/retry attempt gets fresh browser storage and unique poll/organiser identities inside the same invocation's owned pair; the coordinator remains the only table/manifest owner. A top-level rerun gets a new pair.

Zero retries is the acceptance/performance policy. An explicit local diagnostic retry is permissible only with recorded attempt identity, fresh data, retained original failure and all attempts' elapsed time; a recovered retry is flaky evidence, not a clean budget/acceptance pass. CI must not use retries to mask contention. Readiness, eventual-index visibility and observer convergence use bounded condition-based waits; polling expected propagation is different from rerunning an entire failed test. No sleeps as correctness checks or retrying against shared targets.

## Runtime budgets and measurement

These are proposed engineering budgets for T-137, not measured results or already enforced timeouts. Measure headless Chromium with installed dependencies/browser, Node 24, PowerShell 7 and local Docker/DynamoDB, explicit one-worker/zero-retry settings, identical deterministic datasets and no competing test writer. A warm run has an available DynamoDB image/service and cached build/browser; it still creates fresh tables and starts its own API/web processes. Dependency/browser/image downloads and CI artifact upload are outside suite measurements and must be reported separately. Include any build actually performed by the command.

| Selection | Warm browser-stage target | Browser-stage ceiling | Warm whole-command target | Whole-command ceiling |
| --- | --- | --- | --- | --- |
| Fast default | 120 s | 180 s | 180 s (3 min) | 360 s (6 min) |
| Smoke journey | 60 s | 180 s (existing journey ceiling) | 90 s | 360 s (6 min) |
| Focused discovery | 90 s | 180 s | 360 s (6 min), including selected foundation/component/integration stages | 600 s (10 min) |
| Exhaustive pagination/integrity | 300 s (5 min) | 600 s (10 min) | 600 s (10 min), including selected lower-layer integrity stages | 900 s (15 min) |

Browser-stage elapsed time runs from Playwright process start through report completion, including fixtures, seeding, assertions, waits and browser finalizers. Whole-command elapsed time runs from coordinator entry through build/preflight, provision/start, every selected test stage, diagnostic preservation, writer shutdown, owned-table absence confirmation and final summary. A browser-only selection does not include uninvoked lower-layer tests in its coverage claim. Report their durations separately when a layered command invokes them. Aggregate acceptance time is the sum of actual stages/resources and is not subject to the fast-only budget.

Targets describe normal responsiveness; ceilings bound stalls/failure and are not success targets. Exceeding a target must be reported with the slow stage/cases; repeated clean overruns require T-137 tuning or an evidenced, reviewed contract adjustment. Once implemented, exceeding a ceiling returns nonzero even if assertions passed. Do not raise timeouts, skip cases, mock the real sparse query or add retries to make a run appear within budget. Existing 600/180/120/90-second case timeouts do not authorize equally long fast cases; T-137 must reconcile case deadlines with stage budgets.

Reserve the last **60 seconds of each whole-command ceiling** for bounded evidence flush, writer shutdown and table cleanup. The coordinator must stop dispatch/test work by `whole-command ceiling - 60 s`, or sooner at a browser-stage ceiling; earlier setup/lower-layer time reduces the remaining test allowance. Keep the current 90-second service-readiness deadline as an initial upper bound, measured separately. Cold installed-runtime runs may exceed warm targets due to Docker/build startup, but must still respect whole-command ceilings or report failure. CI's outer cancellation deadline must allow the selected command's full ceiling and cleanup plus dependency installation/artifact handling; its current 15-minute job limit is not proof that every tier fits that job. T-139 decides job composition/deadlines.

A ceiling/interruption must enter T-129's teardown path, retain the primary failure and report cleanup independently. If cleanup exceeds its reserve, record failure/remaining targets and safe recovery evidence rather than claiming absence; do not erase evidence or bypass live ownership checks. A forced external kill may leave recovery work. Performance success requires all required cases/checkpoints, zero unexpected skips/failures/retries, and confirmed owned-resource cleanup.

### Evidence and calibration

Existing [T-127 measurements](t127-verification.md#commands-and-results) provide context, not a green fast/exhaustive baseline: the broad 56-case browser batch took 386.30 seconds with 48 passes and 8 selector failures; final verification combined that run with a focused corrected rerun. The corrected 13-case selection took 6.9 seconds in Playwright / 10.18 seconds for the runner. The two isolated smoke runs took 28.5/29.1 seconds in Playwright and 31.4/32.3 seconds for the wrapper. Full component and integration suites took 306.044 and 386.112 seconds respectively; neither is implicitly part of fast, nor a measured duration for the focused discovery selection. Historical [S-036 smoke timings](local-smoke-test-contract.md#s-036-verification-evidence) used earlier lifecycle behavior and remain labelled separately.

T-137 must retain one cold run and at least three consecutive warm runs per selection on the same persisted local database, each with fresh owned resources. Include default and overridden ports, platform/runtime versions, exact revision/selection, dataset sizes, worker/retry settings, total/pass/fail/skip counts, per-stage and slowest-case durations, primary/cleanup outcomes and exact table-absence evidence. Report warm median and maximum and keep every sample, including failures; a small sample is not a reliable p95. Compare higher-worker experiments against that baseline. Diagnose seed cost, full reads, query traversal, index waits, assertion waits and contention separately before adjusting budgets.
